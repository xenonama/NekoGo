# NekoGo

یک فورک از NekoBox با یک رابط کاربری کاملاً جدید (Go + Wails3 + Vue 3).

نسخه‌ی فعلی: **1.0.0-beta.4** (به [تغییرات](#changelog) مراجعه کنید).

## پشته‌ی فناوری

- بک‌اند Go با یک مخزن تنظیمات JSON (بدون دیتابیس).
- پوشش Wails3 (`v3.0.0-beta.20`) که یک سرویس متصل به نام `NekoGo` را در اختیار فرانت‌اند قرار می‌دهد.
- فرانت‌اند Vue 3 + TypeScript با مخازن Pinia و بیلدهای Vite.
- هر موتور خارج از فرآیند اجرا می‌شود. تنظیمات → اتصال → موتور هسته
  موتور ترجیحی را برای پروفایل‌های عادی انتخاب می‌کند: NekoBox Core، sing-box،
  Xray یا Mihomo. اگر آن موتور نتواند پروتکل پروفایل را رندر کند،
  NekoBox Core آن اتصال را بدون تغییر ترجیح ذخیره‌شده مدیریت می‌کند.
  باینری‌های گمشده و خطاهای راه‌اندازی هرگز این جایگزینی را فعال نمی‌کنند. فرمت‌های
  outbound خام و SNI spoof موتور موردنیاز خود را حفظ می‌کنند؛ TUN منحصراً
  مخصوص sing-box می‌ماند.

| موتور | باینری | یادداشت‌ها |
| --- | --- | --- |
| sing-box (فورک) | `nekobox_core.exe` | پیش‌فرض و جایگزین سازگاری. سرور NekoBox Thrift RPC را حمل می‌کند. |
| sing-box (بالادست) | `sing-box.exe` | گزینه‌ی ترجیحی sing-box. نمی‌تواند پروفایل‌های Mieru، Juicity یا TrustTunnel را اجرا کند. |
| Xray | `xray.exe` | گزینه‌ی موتور ترجیحی با آمار gRPC؛ همچنین REALITY/flow را تحت هسته‌ی spoof حمل می‌کند. |
| Clash Meta | `mihomo.exe` | گزینه‌ی موتور ترجیحی. پروفایل را به‌صورت یک گروه select تک‌عضوی رندر می‌کند. |
| Aether | `aether.exe` | اختیاری. ترانسپورت‌های خانواده‌ی MASQUE، به‌علاوه Psiphon. |
| SNI spoof | `sni-spoof.exe` | موتور Rust decoy-ClientHello که از طریق WinDivert هدایت می‌شود. |

یک `xray.exe`، `sing-box.exe`، `mihomo.exe` یا `aether.exe` گمشده
توسط `build.bat` از انتشار رسمی آن دانلود می‌شود (در جایی که
انتشار یک digest منتشر می‌کند، با بررسی SHA256).

## پروتکل‌ها

مستقیماً توسط فرم پروفایل نگاشت می‌شوند و برای هر موتور رندر می‌شوند:

- VLESS (شامل REALITY)، VMess، Trojan، Shadowsocks، SOCKS، HTTP
- Aether: `masque`، `wg`، `gool`، `mim`، `wg-over-masque`، با زنجیره‌های خروجی اختیاری
  Psiphon و Tor (`off` / `chain` / `reverse` / `only`) و ECH

هر چیز دیگری از طریق فیلد **Raw outbound JSON** پروفایل به هسته می‌رسد:

- WireGuard، Hysteria 2 و TUIC — در منوی کشویی پروتکل هستند، اما فرم
  هیچ پارامتری برای آن‌ها حمل نمی‌کند
- Mieru، Juicity و TrustTunnel — اصلاً در منوی کشویی نیستند و بیلد بالادست
  sing-box نمی‌تواند آن‌ها را اجرا کند (هسته‌ی سفارشی)

هسته با بیش از آنچه فرم نشان می‌دهد کامپایل شده است: `build.bat`
`nekobox_core` را با تگ‌های sing-box مربوط به ShadowTLS، Naive، AmneziaWG، Tailscale و gRPC می‌سازد،
بنابراین آن پروتکل‌ها به همین شکل کار می‌کنند — از طریق raw outbound
JSON.

## ایمپورت

چسباندن متن: هر خط یا یک لینک است یا یک URL اشتراک `http(s)://`
که واکشی و باز می‌شود (تا 5000 خط). طرح‌های لینک:
`vless://`، `vmess://`، `trojan://`، `ss://` (SIP002 با پارامترها،
plaintext `method:password@host:port`، و فرم base64 کل لینک سال ۲۰۱۹)،
`socks://` و `aether://`. گزینه‌هایی که فورک نمی‌تواند رعایت کند — مانند
SIP003 `?plugin=` روی `ss://` — به‌عنوان خطا گزارش می‌شوند، هرگز بی‌صدا دور ریخته نمی‌شوند.

## بیلد

`build.bat` را روی ویندوز ۱۰/۱۱ x64 اجرا کنید.

پیش‌نیازها: Go 1.25+، Node.js 20+، Wails3
(`go install github.com/wailsapp/wails/v3/cmd/wails3@latest`)، MinGW-w64،
Rust/cargo (فضای کاری `sni spoofing` یک مرحله‌ی بیلد اجباری است)، و NSIS
(اختیاری — بدون آن هیچ نصب‌کننده‌ای تولید نمی‌شود).

فایل `VERSION` در ریشه‌ی مخزن تنها جایی است که نسخه نوشته می‌شود؛
`build.bat` آن را می‌خواند و GUI، هسته، متادیتای نصب‌کننده و نام‌های
آرتیفکت را مهر می‌زند.

خروجی: `gui/build/bin/nekogo.exe` همراه با `nekobox_core.exe`، `xray.exe`،
`sni-spoof.exe` و موتورهای اختیاری در کنار آن؛ `dist/*.zip` و
`dist/*.exe`.

یک کلون تازه هر چیزی که بیلد نیاز دارد را دارد. فایل `.gitignore` که
از درخت Qt NekoBox به ارث رسیده بود آن را پنهان می‌کرد: یک `*.json` فراگیر
`gui/frontend/package.json`، `package-lock.json`، `tsconfig.json` و
`gui/wails.json` را می‌بلعید، بنابراین `npm install` چیزی برای resolve کردن نداشت و
`wails3 generate bindings` نمی‌توانست اجرا شود، و یک `*.dll` فراگیر
`runtime/WinDivert.dll` را می‌بلعید، که `build.bat` آن را با `if exist` کپی می‌کند — بیلد
BUILD OK چاپ می‌کرد و موتور SNI بدون درایورش ارسال می‌شد.
آن نام‌ها اکنون دوباره گنجانده شده‌اند. `gui/frontend/dist` خروجی بیلد باقی می‌ماند:
`main.go` آن را embed می‌کند، و `build.bat` قبل از `go build` دستورات `npm install` و `npm run build` را اجرا می‌کند،
پس یک کلون هنوز با یک دستور بیلد می‌شود.

## به‌روزرسانی و انتشار

**Updates** درون‌برنامه‌ای هر باینری را از مخزنی که آن را منتشر می‌کند می‌گیرد: انتشارهای این
فورک `nekobox_core.exe`، `xray.exe` و GUI را تأمین می‌کنند، در حالی که
ردیف‌های sing-box، mihomo، GeoIP و GeoSite بالادست از پروژه‌های
خودشان resolve می‌شوند. برای رویه‌ی انتشار و قوانین نام‌گذاری دارایی‌هایی که
به‌روزرسان روی آن‌ها تطبیق می‌دهد، به [docs/PUBLISHING.md](docs/PUBLISHING.md) مراجعه کنید.

`export-source.bat` درخت قابل‌انتشار را در `source\` می‌نویسد، و آخرین
مرحله‌اش از آماده‌برای‌GitHub خواندن آن درخت خودداری می‌کند تا زمانی که هر فایلی درون آن
فهرستی از لینک‌های پروکسی یک‌به‌ازای‌هرخط باشد — یک دامپ اشتراک، که داده است و
نه سورس. یک مخزن عمومی را نمی‌توان از انتشار خارج کرد، بنابراین آن بررسی
آخرین خط است. یک آرگومان دوم (`export-source.bat "" D:\tmp\check`) پاس دهید تا
قوانین include/exclude را روی یک خروجی آزمایشی تست کنید به‌جای
جایگزینی `source\`.

## تغییرات

### 1.0.0-beta.4

- تنظیمات → اتصال → موتور هسته اکنون NekoBox Core، sing-box،
  Xray و Mihomo را ارائه می‌دهد. انتخاب یک ترجیح است: یک پروفایل عادی که
  پروتکلش را موتور انتخاب‌شده نمی‌تواند رندر کند، فقط برای آن
  اتصال از NekoBox Core استفاده می‌کند. باینری‌های گمشده و خطاهای راه‌اندازی هرگز هسته را عوض نمی‌کنند
  یا ترجیح را بازنویسی نمی‌کنند؛ فرمت‌های outbound خام و SNI spoof موتور
  موردنیاز خود را حفظ می‌کنند، و TUN منحصراً مخصوص sing-box می‌ماند.

- چیدمان‌های پنجره‌ای Console و Settings دیگر محتوایشان را جمع نمی‌کنند.
  Traffic، Logs و Connections ارتفاع قابل‌استفاده را در حالت Advanced حفظ می‌کنند، Routing
  Rules در هر دو حالت کاملاً خوانا می‌ماند، و محتوای جدول عریض داخل کارت خودش
  اسکرول می‌شود به‌جای عریض‌تر کردن صفحه.

- لوگوهای NekoGo و Aether می‌توانستند از پنجره بیرون کشیده و روی دسکتاپ
  به‌عنوان فایل تصویری رها شوند. هر رندر لوگوی برنامه اکنون از کشیدن بومی
  تصویر opt-out می‌کند؛ ردیف‌های پروفایل drag-and-drop عمدی خود را حفظ می‌کنند.

- لوگوی ناوبری سفید Aether در حالت روشن نامرئی بود. اکنون در حالت روشن
  مشکی رندر می‌شود و در حالت تاریک طرح اصلی سفید خود را حفظ می‌کند.

- پاک کردن لاگ‌های SNI Spoofing فقط تا زمانی کار می‌کرد که تب ترک شود: پنل
  unmount می‌شد، و بازدید بعدی همان خطوط موتور را دوباره واکشی می‌کرد. پاک کردن
  اکنون یک watermark شناسه‌ی جداگانه در مخزن اتصال است، بنابراین از تعویض تب
  جان سالم به در می‌برد بدون پاک کردن Console اصلی یا تاریخچه‌ی لاگ بک‌اند.

- Console بی‌صدا فقط ۳۰۰ خط جدیدترین را نشان می‌داد. نوار ابزار آن اکنون یک
  انتخابگر محدودیت خط پایدار دارد (100، 300، 500، 1,000 یا 2,000 خط)، به‌علاوه
  **No limit** برای نمایش کل بافر درون‌حافظه‌ای. No limit سقف نمایش را برمی‌دارد؛
  این کار بافر بک‌اند محدود یا تاریخچه‌ی فایل لاگ را نامحدود نمی‌کند.

- Tor به Psiphon به‌عنوان hop خروجی زنجیره پیوست، روی هر دو پایه (تنظیمات →
  Chain، حالت Advanced). پایه‌ی SNI-spoof `aether.exe --tor-only` را با
  upstream تنظیم‌شده روی ترانسپورت spoof‌شده اجرا می‌کند؛ پایه‌ی Aether آن را به‌عنوان
  `tor="chain"` خود موتور اجرا می‌کند، همان شکلی که حالت Psiphon از قبل استفاده می‌کرد —
  یک باینری هر دو را ارسال می‌کند، بنابراین هیچ چیز جدیدی لازم نبود نصب شود. یک پایه یک listener منتشر می‌کند و آمادگی
  روی یک child probe می‌شود، بنابراین یک driver حمل می‌کند: کانفیگی که هر دو را مسلح می‌کند Psiphon را نگه می‌دارد، و
  ذخیره کلید بازنده را با یک خط در لاگ پاک می‌کند به‌جای اینکه یک toggle روی صفحه
  که هیچ کاری نمی‌کند باقی بگذارد. گزینه‌های سطح-زنجیره‌ی Tor (بریج‌های
  `auto`/`first`/`never`/`own`، مخزن رله دایرکتوری، خطوط بریج)
  به گزینه‌های Psiphon بالا می‌پیوندند و از همان قاعده پیروی می‌کنند — پروفایلی که
  خودش را در ویرایشگر Aether تنظیم می‌کند آن‌ها را نگه می‌دارد. listenerهای SOCKS هر دو driver
  قبل از وجود تونل یا circuit پاسخ می‌دهند، بنابراین connect منتظر یک round trip واقعی payload
  از طریق زنجیره می‌ماند: ۱۲۰ ثانیه برای Psiphon، ۳۰۰ ثانیه برای یک Tor سرد
  که باید ابتدا یک consensus دایرکتوری واکشی کند. هیچ کشور خروجی برای انتخاب وجود ندارد —
  Tor خودش انتخاب می‌کند.

- یک connect Aether حامل Tor دیگر در حالی که در حال bootstrap عادی است لغو نمی‌شود.
  موتور listener Tor را فقط در پایان یک bootstrap باز می‌کند و
  `tor="chain"` آن listener را dial می‌کند، بنابراین آمادگی منتظر یک واکشی consensus سرد
  با بودجه‌ی handshake WARP می‌ماند: لاگ
  `aether engine on port 57xxx did not become ready in 30s` را با
  `tor reaching the network: 15%: directory is fetching a consensus` جفت می‌کرد، و
  connect سه بار پشت‌سرهم شکست می‌خورد در حالی که Tor پیشرفت می‌کرد. یک اجرا
  با Tor در مسیر dial‌شده اکنون همان ۳۰۰ ثانیه‌ای را می‌گیرد که پایه‌ی زنجیره‌ی Tor می‌گیرد،
  و لاگ از همان ابتدا این را می‌گوید؛ یک تونل ساده همچنان در ۳۰ ثانیه گزارش می‌دهد.

- چسباندن خطوط بریج در تنظیمات → Chain دیگر آن‌ها را حذف نمی‌کند. جعبه‌های متن آزاد
  آنجا (خطوط بریج Tor، سه فیلد CDN Psiphon) مقدار ذخیره‌شده را نشان می‌دادند و فقط در blur ذخیره می‌کردند،
  در حالی که تب Chain یک بار در ثانیه از polling اتصال دوباره رندر می‌شود — بنابراین یک رندر مجدد جعبه را زیر
  cursor ریست می‌کرد و paste قبل از اینکه بتواند ذخیره شود از بین می‌رفت. متن اکنون
  هنگام تغییر به تنظیمات وارد می‌شود با نوشتن دیسک که دنبالش می‌آید (یک ذخیره در هر
  paste، نه یکی در هر keystroke)، و یک blur یا تعویض تب هر چیزی که
  معلق است را flush می‌کند. هیچ‌چیز تا زمانی که این باز بود به `--tor-bridge` نمی‌رسید، که دلیل
  ظاهراً نادیده گرفته شدن `bridges=own` بود.

- یک زنجیره‌ی Tor که نمی‌تواند دایرکتوری‌اش را واکشی کند اکنون این را می‌گوید، به‌جای اینکه پنج دقیقه ساکت بماند و
  یک escape code نقل کند. probeها روی یک شبکه‌ی فیلترشده — از طریق تونل و بیرون آن، با بریج‌های
  دست‌چین، با فهرست بریج خود موتور، بدون هیچ بریجی — همه در
  همان نقطه متوقف شدند: handshake بریج‌ها، guardها خود را قابل‌استفاده گزارش می‌کنند، و
  دانلود consensus کوتاه برمی‌گردد
  (`tor_dirclient: Retiring circuit because of directory failure: Partial
  response`)، بعد از آن موتور همان دانلود را برای همیشه دوباره شروع می‌کند. کنسول
  نمی‌توانست آن را نشان دهد: arti هر خطی که می‌نویسد را رنگ‌آمیزی می‌کند، بنابراین لاگ با `\x1b[2m…`
  پر می‌شد، و شکست یکی از آن خطوط رنگی را به‌عنوان "آخرین خروجی" نقل می‌کرد.
  کدهای رنگ اکنون هر جا که خروجی یک هسته وارد لاگ می‌شود (viewer، حلقه‌ی last-lines، گزارش‌های شکست)
  حذف می‌شوند، وضعیت تسلیم خود هسته (`[-] tor … Stuck at 15%: Can't bootstrap a Tor
  directory`) به‌محض ظاهر شدن به‌عنوان هشدار لاگ می‌شود، و انتظار با آن دلیل و
  تنظیمی که باید تغییر کند به پایان می‌رسد به‌جای `did not become ready
  in 5m0s`. خود دانلود ناقص وظیفه‌ی هسته است — NekoGo اکنون حداقل می‌تواند بگوید کدام
  از تنظیماتش هنوز حرفی برای گفتن دارند.

- خطوط بریجی که ذخیره کرده‌اید اما استفاده نمی‌کنید اکنون نام برده می‌شوند، در تب Chain و
  در لاگ. فقط `bridges=own` خطوط را به موتور می‌دهد، و ویرایشگر
  فقط زیر `own` رندر می‌شود، بنابراین دور کردن picker بعد از یک paste خطوط را ذخیره‌شده،
  نامرئی و بی‌استفاده باقی می‌گذاشت — connect سپس کل ۳۰۰ ثانیه را روی
  واکشی‌ای که `auto` انجام می‌دهد منتظر می‌ماند. تب اکنون آن‌ها را می‌شمارد
  ("4 bridge lines saved, and auto does not hand them to the engine")، و هر دو
  پایه‌ی Tor آن تفاوت را به‌محض شروع به‌عنوان هشدار لاگ می‌کنند، از
  آرگومان‌هایی که قرار است اجرا کنند، بنابراین یک اجرا نمی‌تواند شکلی را ادعا کند که
  ندارد. یک دستور موتور دست‌نویس دست‌نخورده می‌ماند: بریج‌های خودش را می‌آورد.

- موتور Psiphon می‌گوید آیا اینجاست، و می‌تواند نصب شود. آن `aether.exe` است و ترانسپورت‌های بریجش
  در `bin\pt\` زندگی می‌کنند، اما هیچ چیز در برنامه هیچ‌کدام را نام نمی‌برد: تب Updates هر
  هسته‌ی دیگری را فهرست می‌کرد و هیچ ردیفی برای آن نداشت، بنابراین "آیا موتور Psiphon نصب است؟"
  هیچ جا پاسخی نداشت — و یک `pt\lyrebird.exe` گمشده به‌عنوان یک توقف bootstrap خوانده می‌شد
  نه به‌عنوان یک فایل گمشده. تنظیمات → Updates یک ردیف "Aether" گرفت
  (قبلاً به‌اشتباه "Psiphon engine (aether)" نامیده می‌شد؛ موتور همان هسته‌ی Aether است) که
  انتشار `CluvexStudio/Aether` را می‌خواند: نسخه را گزارش می‌دهد،
  وقتی موتوری نیست "Not installed" می‌گوید، و وقتی موتور حاضر است اما ترانسپورت‌هایش نیستند

- Tor و Psiphon دو موتور هستند و اکنون دو ردیف Update دارند. "Tor" نام دیگر

- hop Tor زنجیره اکنون روی آن `tor.exe` هر زمان که ماشین یکی دارد اجرا می‌شود. قبل از این،
  hop همیشه Arti لینک‌شده‌ی aether بود، که در ۱۵٪ bootstrap خود روی مسیر spoof‌شده متوقف می‌شود
  — بریج‌ها handshake را حمل می‌کنند، هیچ دایرکتوری از طریق آن‌ها برنمی‌گردد — جایی که daemon مستقل پشت
  همان SOCKS fronted به `Bootstrapped 100%` می‌رسد و ترافیک را حمل می‌کند (دو
  رفتاری که driver Arti هرگز مجبور نبود مدل کند: `tor.exe` پورت SOCKS خود را در ۰٪ باز می‌کند، بنابراین آمادگی اکنون
  منتظر خط ۱۰۰٪ خود daemon می‌ماند قبل از اینکه listener را probe کند، و consensus و guard set آن
  در یک `tor-state\` پایدار کش می‌شوند به‌جای یک دایرکتوری per-connect که هر
  شروع را مجبور می‌کند کل واکشی را دوباره بپردازد). خطوط بریج ذخیره‌شده به‌عنوان
  `--UseBridges 1` + `--Bridge` + یک `--ClientTransportPlugin` که باینری ترانسپورتی را که هر نوع را سرو می‌کند نام می‌برد می‌روند، و یک خطی که این daemon نمی‌تواند dial کند
  — یک fingerprint که ۴۰ رقم hex نیست، یک خط webtunnel بدون `url=` front،
  یک ترانسپورتی که هیچ چیزی کنار `tor.exe` سرو نمی‌کند — با یک هشدار که شکلش را توصیف می‌کند و هرگز خط را تکرار نمی‌کند
  کنار گذاشته می‌شود، چون یک خط بدشکل یک شکست کانفیگ است که اجرا را قبل از شروع متوقف می‌کند. یک
  ماشین بدون `tor.exe` همچنان زنجیره می‌کند: پایه به Arti برمی‌گردد، و
  لاگ نام می‌برد کدام موتور hop را حمل کرد. یک `tor.exe` سرگردان که یک GUI کرش‌شده
  رها کرده در راه‌اندازی با سایر موتورها reap می‌شود.

- hop Tor پایه‌ی Aether همان تفکیک را می‌گیرد. `Aether → Tor` قبلاً به معنای
  یک پرچم بیشتر روی موتور بود — `--tor`، بنابراین Arti لینک‌شده‌اش از طریق
  تونل MASQUE که همین الان ساخته بود dial می‌کرد — و آن کلاینت هم اینجا در ۱۵٪ متوقف می‌شود:
  تونل در چند ثانیه بالا می‌آید، دایرکتوری هرگز از طریق آن برنمی‌گردد، و connect روی
  `aether engine on port 49457 did not become ready in 5m0s` می‌میرد. با یک `tor.exe`
  روی ماشین، موتور اکنون تونل را تنها حمل می‌کند و daemon به‌عنوان یک child دوم پشت آن اجرا می‌شود،
  و تونل را به‌عنوان front SOCKS خودش dial می‌کند، در حالی که outbound aether ترانسپورت
  در برابر listener daemon رندر می‌شود به‌جای listener موتور. Connect لاگ می‌کند کدام یک از این دو را انتخاب کرد،
  و یک daemon که تونلش در میانه‌ی bootstrap مرده را رد می‌کند به‌جای اینکه پنج دقیقه‌اش را برای frontی که رفته منتظر بماند.
  در جایی Arti می‌ماند که تفکیک چیزی را می‌گیرد: هیچ `tor.exe` روی ماشین، پروفایلی که
  `Aether.Command` دست‌نویسش خروجی‌های خودش را نام می‌برد، و پروفایلی که Psiphon را هم زنجیره می‌کند
  — یک driver در هر پایه، و آنجا Psiphon مالک listener dial‌شده است. hop عضوی از
  گروه commit‌شده است، بنابراین مرگش connect را پایین می‌آورد، یک rollback daemon را قبل از تونلی که dial می‌کند متوقف می‌کند، و یک
  reconnect چسبنده هرگز یک child از یک پایه‌ی دو-child را به connect بعدی تحویل نمی‌دهد.

- بودجه‌ی آمادگی Tor اکنون از کشی که اجرا می‌تواند سوارش شود پیروی می‌کند. اندازه‌گیری‌شده با
  daemon پشت یک تونل MASQUE روی بریج‌هایی که این کاربر چسباند: اولین
  bootstrap `5m43s` طول کشید، و یکی بعد از آن — که consensus را از
  دایرکتوری state که اولی رها کرده بود می‌خواند — `9s` طول کشید. پنج دقیقه
  بنابراین کافی بود تا اولین connect یک نصب را شکست دهد و در هر connect بعدی موفق شود،
  که این‌طور می‌شود که "aether connects but tor does not" به‌عنوان متناوب خوانده می‌شود.
  یک hop که دایرکتوری state آن خالی است اکنون ده دقیقه می‌گیرد و لاگ می‌کند
  `no Tor directory cached under … yet, so this bootstrap gets
  10m0s for its first fetch instead of 5m0s`؛ پایه‌ای که فراخوان از قبل فکر می‌کند طولانی‌تر است هرگز کوتاه نمی‌شود.
  پایه‌ی `--tor-only` Arti هر بار همان بودجه را می‌گیرد، چون در یک `--tor-dir` اجرا می‌شود
  که برای connect ساخته و توسط connect بعدی حذف می‌شود، بنابراین هرگز اجرای دوم نیست.
  خود خطوط بریج هم ارزش یک نگاه را دارند: `tor.exe` هر یک را dial می‌کند، بنابراین یک
  غیرقابل‌دسترس — یک بریج بازنشسته، یا خطی که یک fixture تست چسبانده — دقیقه‌ها تلاش مجدد
  قبل از تمام شدن واکشی است.

- زنجیره‌ای که این connect اجرا نمی‌کند اکنون نام برده می‌شود به‌جای اینکه بی‌صدا بی‌استفاده بماند.
  کلیدهای تب Chain به یک پایه تعلق دارند: `SNI spoof → Tor/Psiphon` نیاز به
  پروفایلی دارد که از موتور spoofing عبور کند، `Aether → Tor/Psiphon` نیاز به
  یکی دارد که خودش یک تونل Aether است و هیچ حالت خودش را نام نمی‌برد.
  مسلح کردن Tor و متصل کردن یک گره عادی یک وضعیت "connected" عادی تولید می‌کرد بدون هیچ Tor
  در مسیر و هیچ چیزی که این را بگوید. Connect اکنون پایه‌ای را که رد کرد و دلیلش را لاگ می‌کند
  — `the Aether Tor chain is armed, but "My SS" is not an
  Aether node: the engine runs no Tor on this connect` — و وقتی
  زنجیره واقعاً اجرا می‌شود ساکت می‌ماند، شامل پروفایلی که `tor=chain` خودش را می‌آورد
  به‌جای کلید.

- آن بررسی اکنون مال کل connect است، نه یک موتور. هر پورت ثابت/شناخته‌شده‌ای که
  connect bind خواهد کرد ابتدا جمع‌آوری می‌شود — inbound مختلط، پورت دوم Xray
  و listener API، listenerهایی که یک دستور Aether دست‌نویس نام می‌برد،
  inboundهایی که یک override کانفیگ خام bind می‌کند — و همه‌شان قبل از وجود اولین child
  منتظر می‌مانند و رد می‌شوند. پورت external-controller مایهمو بعداً انتخاب می‌شود و
  بخشی از این preflight پورت-ثابت نیست. Xray و mihomo قبلاً یک پورت گرفته‌شده را فوراً رد می‌کردند،
  بنابراین یک socket که connect قبلی هنوز آزادش می‌کرد یک کلیک هزینه داشت؛ آن‌ها اکنون همان پنجره‌ی دو ثانیه‌ای را دارند.
  پورت‌هایی که برنامه خودش در حین connect انتخاب می‌کند (listener یک hop زنجیره،
  پورت SOCKS یک daemon Tor) همان‌طور که انتخاب می‌شوند claim می‌شوند، بنابراین یک picker بعدی نمی‌تواند
  همان شماره را به پایه‌ی دوم بدهد — hop Arti listener خود را فقط در پایان
  bootstrap خود bind می‌کند، دقیقه‌هایی که در طول آن پورت برای همه‌ی دیگران آزاد به نظر می‌رسید.
  موتوری که listener خودش گرفته شده اکنون با شماره‌ی پورت قبل از شروع
  بودجه‌ی آمادگی‌اش این را می‌گوید، به‌جای اینکه پنج دقیقه صرف کند و یک timeout گزارش دهد؛ و چون
  برنامه آن listener را شماره‌گذاری می‌کند، راه‌حلش می‌گوید هر چیزی که آن را گرفته ببندید
  به‌جای تغییر تنظیمی که نمی‌تواند آن را جابه‌جا کند.

- آن بررسی اکنون هر listenerی را که یک اجرای Aether bind می‌کند پوشش می‌دهد، نه فقط
  آن یکی که برنامه dial می‌کند. با Tor یا Psiphon داخل تونل موتور
  روی سه شماره‌ی متوالی گوش می‌دهد (`--bind`، `--tor-bind`،
  `--psiphon-bind`)، و فقط dialed one نگاه می‌شد: پورتی که دو شماره بالاتر گرفته شده بود به موتور داده می‌شد،
  که سپس در bind آن شکست می‌خورد و کل بودجه‌ی آمادگی‌اش را بدون گفتن چیزی صرف می‌کرد.
  یک محدوده‌ی کاندید اکنون رد می‌شود مگر اینکه هر شماره در آن روی TCP *و* UDP آزاد باشد (موتور
  هر دو را bind می‌کند) و توسط پایه‌ی دیگری از همان connect claim نشده باشد،
  و کل محدوده همان‌طور که انتخاب می‌شود claim می‌شود.

- یک connect می‌توانست روی ماشینی با هزاران پورت آزاد با `no loopback port free for TCP and UDP`
  شکست بخورد. ویندوز باندهای UDP پیوسته را داخل محدوده‌ی ephemeral رزرو می‌کند
  (WinNAT/Hyper-V — نُه تا اینجا، شامل 64826-65025)، و kernel به یک bind `:0`
  با *شماره‌ی بعدی* در توالی پاسخ می‌دهد، بنابراین هر پنج تلاش مجدد در باندی فرود آمدند که
  اولی در آن رد شده بود: 64844، 64850، 64855، 64869، 64878. موتور Aether،
  hop daemon Tor و mihomo همه listener خود را از طریق
  آن یک تابع انتخاب می‌کنند، بنابراین کل connect روی آن مرد. بعد از یک امتناع،
  picker اکنون به یک پورت تصادفی در محدوده می‌پرد به‌جای اینکه شماره‌ی بعدی را بخواهد،
  و همچنان شماره‌ای را که پایه‌ی دیگری از connect claim کرده رد می‌کند.

- یک connect Aether دیگر در ۳۰ ثانیه در حالی که هنوز کار می‌کند کشته نمی‌شود. یک scan MASQUE
  روی یک شبکه‌ی فیلترشده در ۴۸ ثانیه پاسخ SOCKS می‌داد، و مهلت سخت موتور را در ۳۰ پایین می‌آورد
  — بنابراین connect شکست می‌خورد و تلاش مجددی که بالاخره کار می‌کرد شانس بود، نه یک اصلاح.
  آمادگی اکنون در دورهای ۳۰ ثانیه‌ای تا زمانی که child زنده است و همچنان صحبت می‌کند منتظر می‌ماند،
  همان‌طور که کلاینت مرجع انجام می‌دهد ("a scan may take minutes")، و هر دوری که می‌گذرد
  این را در لاگ می‌گوید به‌جای اینکه اجرا را پایان دهد. مرزها مال خود موتور است: خارج می‌شود، می‌گوید
  نمی‌تواند ادامه دهد، یک دور کامل بعد از نام بردن یک توقف ساکت می‌شود (یا
  بعد از یک bootstrap Tor که قبل از یک circuit متوقف شد)، یا یک Disconnect این spawn را متوقف می‌کند.

- کلمات خود موتور اکنون آن انتظار را پایان می‌دهند، با دلیلی که داده است.
  سه تا از آن‌ها لاگ می‌شدند و سپس نادیده گرفته می‌شدند در حالی که probe همچنان از
  listenerی می‌پرسید که هرگز ترافیک حمل نمی‌کرد: carrier داخل تونل که پایانش را گزارش می‌کند
  (`[-] tor: … circuit failed`، معادل Psiphon)، `ECH is on but there is no ECH key to offer`
  (هسته متوقف می‌شود به‌جای ارسال نام سرور در کلیر — پیام اکنون
  می‌گوید ECH را خاموش کنید یا resolverی را نام ببرید که می‌تواند کلید را واکشی کند)، و یک
  خط `Error:` خالی. هر کدام با کلمات خود هسته گزارش می‌شوند به‌جای یک timeout دقیقه‌ها بعد.

- یک endpoint Aether ذخیره‌شده که مرده دیگر برای همیشه pin نمی‌شود.
  موتور اعلام می‌کند `last known-good gateway … no longer responds;
  rescanning` و سپس همچنان peer اجباری را دوباره استفاده می‌کند (`probe skipped`)،
  بنابراین همان gateway مرده را dial می‌کند تا کشته شود — اندازه‌گیری‌شده در ۱۷۰ ثانیه
  بدون listener، در حالی که همان پروفایل بدون pin در ۴۸ ثانیه scan و پاسخ داد. Connect اکنون
  موتور را یک بار دیگر بدون pin اجرا می‌کند، همان‌طور که Scan خود برنامه انجام می‌دهد، و می‌گوید از کدام endpoint دست کشید.

  chrome-120 پتن برای آن وجود دارد؛ درخواست آن اینجا قبلاً به معنای نوشتن کل
  دستور با دست بود.

- تب Aether پنجره‌ی WARP keys پتن را به‌عنوان یک کارت گرفت: هویت‌های WARP جدید
  می‌توانند بدون ترک تب ثبت شوند. این کارت انواعی را که aether 2.3.0 واقعاً می‌پذیرد ارائه می‌دهد
  (`all`، `wg`، `masque`، `gool`، `mim`)، آدرس API، fragment و ECH ClientHello برای
  فراخوانی‌های WARP API، TLS fingerprint، و یک carrier اختیاری Tor یا Psiphon برای شبکه‌هایی
  که API را کاملاً مسدود می‌کنند. هویت‌های در حال استفاده با device id و آدرس‌های
  تخصیص‌یافته‌شان فهرست می‌شوند. یک اجرا کلیدهای جدید را کنار آن‌ها staged می‌کند و
  آن‌ها را فقط زمانی به جای خود منتقل می‌کند که هر فایل از آن نوع به‌عنوان یک
  هویت خوانده شود، بنابراین یک ثبت ناموفق یا لغوشده کلیدهایی که کار می‌کنند را حفظ می‌کند؛
  کلیدهای جدید از اتصال بعدی استفاده می‌شوند. کارت از شروع در حین
  بالا بودن یک تونل یا اجرای یک scan خودداری می‌کند، و می‌گوید کدام. نام سرور API،
  میزبان API و ردیف‌های exit-node پتن حذف شده‌اند — آن‌ها به یک فورک جدیدتر
  تعلق دارند، و این هسته آن‌ها را رد می‌کند.

- کلید "Bundled server list" روی یک hop Psiphon اکنون آنچه می‌گوید را انجام می‌دهد. آن
  ذخیره و رندر می‌شد اما هرگز به موتور نمی‌رسید، بنابراین هر اتصال اول
  همچنان باید فهرست سرور Psiphon را دانلود می‌کرد — همان واکشی‌ای که یک شبکه‌ی فیلترشده
  قبل از شروع تونل مسدود می‌کند. NekoGo اکنون آن فهرست را ارسال می‌کند (bundle امضاشده‌ی خود Psiphon، ۴۲۶ ورودی،
  بررسی‌شده در برابر کلید امضای واقعی) و آن را به هسته با `--psiphon-server-entries` تحویل می‌دهد،
  در پوشه‌ی پروفایل باز می‌شود. هسته هر چیزی که واکشی می‌کند را روی
  آن ادغام می‌کند، بنابراین فهرست ارسالی یک bootstrap است نه یک سقف؛ تنظیمات →
  Updates → "Psiphon Servers" می‌تواند آن را با یک فهرست امضاشده‌ی جدیدتر جایگزین کند بدون
  انتظار برای بیلد بعدی NekoGo.

- یک پروفایل Aether با یک hop Psiphon دیگر در حین اتصال کشته نمی‌شود.
  آمادگی در دورهای سکوت اندازه‌گیری می‌شود و دور ساده‌ی موتور ۳۰ ثانیه است، اما Psiphon
  در حین واکشی tactics اصلاً چیزی نمی‌گوید: یک اجرای زنده روی یک شبکه‌ی فیلترشده ۵۴ ثانیه هیچ چیزی چاپ نکرد و سپس
  با یک خروجی کارکننده آماده بالا آمد. hop اکنون همان دور ۱۲۰ ثانیه‌ای را می‌گیرد که پایه‌ی زنجیره‌ی Psiphon
  از قبل داشت، و دور طولانی‌تر Tor همچنان وقتی هر دو carrier روشن‌اند برنده می‌شود.
  خط لاگی که carrier را نام می‌برد اکنون آن یکی که واقعاً در مسیر dialed است را نام می‌برد
  به‌جای اینکه همیشه Tor بگوید.

- ویرایشگر Proxies می‌تواند دوباره یک پروفایل دو-hop Aether را ذخیره کند. `gool`، `mim`
  و `wg-over-masque` یک جفت outer/inner dial می‌کنند نه یک endpoint، بنابراین
  ویرایشگر ردیف‌های آدرس و پورت را پنهان می‌کند — اما مسیر ذخیره همچنان
  یک پورت در 1..65535 می‌خواست و پروفایل را با `Port must be
  1..65535 (got 0)` رد می‌کرد، شامل یکی که تب Aether همین الان نوشته بود. یک پروفایل
  که ردیف endpointش پنهان است اکنون معاف است، همان‌طور که یک پروفایل raw-outbound
  از قبل بود. یک پروفایل تک-hop Aether با یک پورت غیرقابل‌استفاده همچنان
  رد می‌شود.

- فهرست سرور دیگر endpointی را چاپ نمی‌کند که یک پروفایل Aether dial نمی‌کند. یک پروفایل دو-hop یا فقط-carrier
  هیچ آدرسی و پورت ۰ حمل نمی‌کند، و هر فهرستی `:0` را نشان می‌داد — کارت Home و
  برچسب screen-reader ردیف هم شامل — مثل اینکه آنجا جایی است که متصل می‌شود. آن ردیف‌ها اکنون
  `scan` می‌گویند، یا `via psiphon` / `via tor` وقتی یک carrier تنها اجرا می‌شود، و یک
  endpoint بیرونی pin‌شده همان‌طور که نوشته شده نشان داده می‌شود. یک پروفایل تک-hop با یک آدرس خالی
  به همان دلیل `:443` می‌گفت و اکنون `scan` هم می‌گوید، مطابق "blank = scan" خود
  ویرایشگر.

- ذخیره‌ی هر تنظیمی دیگر نتایج scan SNI یافت‌شده از زمان شروع
  برنامه را دور نمی‌ریزد. مسیر ذخیره فیدها، نتایج scan Aether و overrideهای هسته
  را از دیسک حمل می‌کرد، اما فهرست‌های آدرس و نام SNI از
  snapshotی می‌آمدند که فرانت‌اند یک بار در راه‌اندازی بارگذاری می‌کرد — بنابراین یک scan که تمام شده بود، یا
  لغو شده بود (که همچنین آنچه یافته را ذخیره می‌کند)، توسط ذخیره‌ی تنظیمات نامرتبط بعدی بازنویسی می‌شد.
  هر دو فهرست اکنون به همان شکل حمل می‌شوند.

- یک تست تأخیر روی یک پروفایل Aether متصل با یک hop زنجیره‌ی Tor زنجیره را اندازه می‌گیرد.
  این تست listener SOCKS خود موتور تونل را dial می‌کرد به‌جای پورت منتشرشده،
  که برای یک hop واقعی tor.exe همان listener daemon است — بنابراین تست Tor را دور می‌زد و
  تأخیر فقط-WARP را به‌عنوان زنجیره گزارش می‌کرد، و یک hop که از طریق Tor route می‌شود
  کندتر از WARP تنها به نظر نمی‌رسید.

- یک disconnect یا یک خطای موتور که با یک connect جدیدتر مسابقه می‌دهد دیگر
  listener موتور جدید را پنهان نمی‌کند. متوقف کردن یک موتور Aether می‌تواند سه ثانیه
  طول بکشد تا درخت فرآیندش را reap کند، و یک connectی که داخل آن پنجره شروع شده بود
  پورت dial خود را منتشر کرد فقط برای اینکه stop قدیمی‌تر آن را پاک کند: هسته سپس
  "no engine" رندر کرد در حالی که aether.exe سالم بود و سرو می‌کرد — connected،
  no traffic. یک stop اکنون فقط پورتی را که مالکش بود unpublish می‌کند.

- یک نصب ناموفق WARP key می‌توانست برخی هویت‌های موجود را جایگزین کند در حالی که گزارش می‌داد هیچ‌کدام تغییر نکرده.
  کلیدهای موجود اکنون قبل از جایگزینی کنار گذاشته می‌شوند تا یک نصب ناموفق بتواند rollback کند.
  کلیدهای staged کپی می‌شوند به‌جای جابه‌جا شدن، و تمدید را برای یک تلاش بعدی حفظ می‌کنند. این
  rollback روی خطاهای فایل گزارش‌شده است، نه یک تراکنش چندفایلی اتمیک نسبت به کرش.

- یک ویرایش در کارت WARP keys اگر تب را در کمتر از نیم ثانیه بعد از تایپ ترک می‌کردید از بین می‌رفت.
  کارت یک بار که تایپ آرام می‌شود ذخیره می‌کند، و ترک تب Aether آن را تخریب می‌کند — که
  ذخیره‌ی معلق را لغو می‌کرد به‌جای نوشتنش، بنابراین فیلد وقتی برمی‌گشتید خالی بود.
  ویرایش معلق اکنون در راه خروج نوشته می‌شود.

- یک دستور ثبت WARP سفارشی اکنون فایل‌های کلید مورد انتظار و نوع پیشرفت را تعیین می‌کند.
  قبلاً dropdown همچنان آن بررسی‌ها را کنترل می‌کرد:
  `--register wg` می‌توانست بعد از موفقیت شکست بخورد، در حالی که یک ثبت `mim` ناقص می‌توانست پاس شود
  وقتی dropdown فقط `masque` درخواست می‌کرد. انواع ثبت گمشده یا پشتیبانی‌نشده
  قبل از شروع رد می‌شوند.

- یک کپی ناموفق هویت WARP اکنون مقصدی را که ایجاد کرده حذف می‌کند،
  به‌جای اینکه یک فایل خالی یا ناقص رها کند که تلاش مجدد را مسدود کند. فایل‌های موجود
  وقتی یک کپی رد می‌شود دست‌نخورده باقی می‌مانند.

- لغو Connect اکنون در preflight، شروع موتور و تنظیم پروکسی
  سیستم اتمیک است. یک cancel تلاش سطح-برنامه و generation شروع
  manager هسته را باطل می‌کند، شامل یک Stop که قبل از resolve شدن هسته می‌رسد، تلاش کهنه را تخلیه می‌کند قبل از اجازه دادن به یکی دیگر،
  یک پروکسی نصب‌شده توسط تلاش لغوشده را برمی‌گرداند، و هیچ شکست قرمزی برای
  Cancel خود کاربر گزارش نمی‌کند. tray به‌محض شروع راه‌اندازی Cancel connection را تبلیغ می‌کند
  و وقتی تلاش تخلیه می‌شود آن را پاک می‌کند.

- یک Connect که بعد از انتخاب سرور دیگری توسط کاربر تمام می‌شود دیگر
  انتخاب قدیمی را به دیسک بازنویسی نمی‌کند. به‌روزرسانی‌های پروفایل فعال اکنون مقداری را که قبل از راه‌اندازی دیده شده مقایسه می‌کنند
  و فقط تا زمانی که همچنان جاری است persist می‌کنند، شامل مسیر relaunch با دسترسی بالا.

- جایگزینی یک آدرس اشتراک وقتی هر لینک تجزیه‌شده اعتبارسنجی را رد می‌کند دیگر
  آدرس غیرقابل‌استفاده را ثبت نمی‌کند یا فید کارکننده را به آن اشاره‌گر باقی نمی‌گذارد. آدرس جدید
  برگردانده می‌شود و تعداد رد گزارش می‌شود؛ جایگزینی‌های فقط-تکراری معتبر می‌مانند.
  پروفایلی که نوشتن دیسکش شکست می‌خورد هم از حافظه حذف می‌شود، بنابراین نمی‌تواند زیر یک ذخیره‌ی بعدی دوباره ظاهر شود؛
  نوشتن‌های ردشده‌ی کل-تنظیمات و پروفایل-فعال هم مقادیر درون‌حافظه‌ای قبلی خود را بازمی‌گردانند.

- مهاجرت کانفیگ قدیمی فقط تنظیمات شناخته‌شده‌ی فایل‌سیستم را بازنویسی می‌کند (مسیرهای هسته و
  موتور، مسیرهای خروجی/لاگ و GeoIP). نام پروفایل‌ها، رمزها، آدرس‌های اشتراک، URLهای تست
  و raw outbound JSON دیگر فقط به‌خاطر اینکه متنشان شامل `NekoBox` است تغییر نمی‌کنند.

- انتخابگر Core ویرایشگر پروفایل اکنون فقط برای raw outbound JSON ظاهر می‌شود،
  جایی که طرح JSON را انتخاب می‌کند و فقط sing-box، Xray و Mihomo را ارائه می‌دهد.
  پروفایل‌های عادی می‌گویند که موتورشان از تنظیمات → Connection می‌آید،
  و نه فهرست Proxies و نه Advanced Config یک پروفایل عادی را به‌عنوان Mihomo برچسب نمی‌زند یا مسدود نمی‌کند
  فقط به‌خاطر اینکه فیلد core قدیمی‌اش این را می‌گوید.

- ذخیره‌های ردشده‌ی تم، حالت Simple/Advanced، آخرین-تب و peek اکنون تنظیم
  تأثیرگرفته را برمی‌گردانند به‌جای اینکه کنترلی که یک مقدار ذخیره‌نشده را ادعا می‌کند رها کنند؛
  یک تم ردشده هم کلاس DOM را بازمی‌گرداند. نوشتن‌های کل-تنظیمات
  سریال‌سازی می‌شوند، و یک نوشتن ناموفق فقط فیلدهایی را برمی‌گرداند که هیچ اقدام جدیدتری
  تغییرشان نداده، با استفاده از آخرین مقدار موفق persist‌شده بنابراین حتی تغییرهای ناموفق مکرر نمی‌توانند یک
  حالت میانی ذخیره‌نشده رها کنند. کنترل‌های Sidebar، theme و mode شکست‌ها را در shell
  آشکار می‌کنند، شکست‌های انتخاب سرور دیگر بی‌صدا نیستند، و انتخاب آفلاین محلی می‌ماند.

### 1.0.0-beta.3

- لینک‌های `ss://` که یک query string حمل می‌کنند (`ss://…@1.2.3.4:443?#name`،
  شکلی که تولیدکنندگان لینک منتشر می‌کنند) اکنون ایمپورت می‌شوند به‌جای شکست با
  `ss: bad port "443?"`. userinfo base64 علائم نگارشی `+` و `=` خود را حفظ می‌کند،
  و یک لینک SIP003 `?plugin=` با نام رد می‌شود به‌جای اینکه بی‌صدا
  به‌عنوان پروفایلی ایمپورت شود که نمی‌تواند متصل شود.

- پروفایلی که raw outbound آن literal JSON `null` است قبلاً
  سازندگان کانفیگ sing-box، Xray و mihomo را در Connect پنیک می‌کرد؛ هر کدام اکنون
  یک خطای کانفیگ برمی‌گردانند.

- ویرایشگر کانفیگ خام یک سند خالی یا `null` را رد می‌کند. قبلاً پذیرفته می‌شد،
  هر override بخش را پاک می‌کرد، و کانفیگی به موتور می‌داد که
  نمی‌توانست راه‌اندازی شود. پروفایل‌هایی که قبلاً این‌طور ذخیره شده‌اند اکنون به
  رندر پیش‌فرض خودشان برمی‌گردند.

- هرمتیک بودن مجموعه‌ی تست: تست‌های ایمپورت و کانفیگ فقط در پوشه‌ی موقت
  خودشان می‌نویسند. قبلاً `%APPDATA%\NekoGo\config.json` زنده را بارگذاری — و می‌توانستند بازنویسی — کنند.

- گره‌ای با برچسب `%` خالی (`…#100%`، روشی که بسیاری از تولیدکنندگان
  برچسب پهنای باند را می‌نویسند) قبلاً کل ایمپورت را با
  `invalid URL escape "%"` شکست می‌داد، و برچسبی حاوی `%XX` دو بار decode می‌شد،
  و `a%41b` را به `aAb` تغییر نام می‌داد. برچسب اکنون قبل از
  تجزیه از لینک جدا می‌شود و دقیقاً یک بار decode می‌شود، برای هر پروتکل مبتنی بر `url.Parse`.
  یک `%` خالی داخل رمز `trojan`/`vless`/`socks` لینک را دقیقاً به
  همان شکل رد می‌کرد — Go کل URL را به خاطر یک escape نامعتبر رد می‌کند —
  بنابراین اعتبارنامه‌ها اکنون برای تجزیه escape می‌شوند و همچنان یک بار decode می‌شوند.

- لینک‌های اشتراک `vless`/`trojan`/`ss`/`socks` برچسب‌ها، اعتبارنامه‌ها و مسیرهای WebSocket
  خصمانه را بایت‌به‌بایت round-trip می‌کنند (`@Delta`، `100%`،
  `p@ss:word/with?s`، `/ws?ed=2560`، غیر-ASCII).

- دانلودهای اشتراک دیگر به یک redirect به loopback،
  RFC1918، link-local/metadata، CGNAT یا `localhost` دنبال نمی‌کنند. URL فید
  با یک تایمر دوباره واکشی می‌شود، بنابراین redirect یک درخواست انتخاب‌شده توسط سرور
  علیه شبکه‌ی خود کاربر بود که هیچ‌کس به آن نگاه نمی‌کرد.

- فیدی که دانلود نمی‌شود اکنون دلیلش را در لاگ می‌گوید (یک 403، یک redirect ردشده، یک بدنه‌ی خالی همه
  قبلاً مثل `0 new profiles, 1 invalid` به نظر می‌رسیدند). پیام ابتدا از `*url.Error`
  در net/http باز می‌شود: متنش URL درخواست را تکرار می‌کند، و یک URL فید
  access token را در query خود حمل می‌کند — و این فایل لاگ همان چیزی است که کاربران هنگام درخواست
  کمک تحویل می‌دهند.

- دانلود GeoIP که یک دیتابیس MaxMind قابل‌بازکردن نیست قبل از جایگزینی
  نصب‌شده رد می‌شود. آن منبع هیچ sha256 منتشر نمی‌کند،
  بنابراین یک بدنه‌ی ناقص یا یک صفحه‌ی خطای HTML قبلاً روی دیسک فرود می‌آمد، نشانگر بازبینی را به‌روز می‌کرد
  و بی‌صدا هر جست‌وجوی کشوری را بدون مسیر تلاش مجدد باقی‌مانده تخریب می‌کرد.

- لغو یک بازخوانی کشور دیگر بازخوانی‌ای را که بعد از آن شروع شده unregister نمی‌کند.
  `CancelRefreshCountries` اسلات یک‌در-یک‌بار را آزاد می‌کند تا UI
  بتواند فوراً دوباره تلاش کند، اما اجرای لغوشده قبلاً هر چیزی را که تا زمان پایان تخلیه ثبت شده بود پاک می‌کرد:
  بازخوانی جدیدتر از خوانش پیشرفت "N/M" ناپدید می‌شد، دکمه‌ی Cancel آن بی‌اثر می‌شد، و
  نگهبان already-running اجازه می‌داد بازخوانی‌های انباشته همزمان روی یک مجموعه شمارنده اجرا شوند.
  ثبت‌ها اکنون شماره‌گذاری شده‌اند و یک اجرا فقط خودش را پاک می‌کند.

- `ss://aes-256-gcm:pa=ss@host:port` و سایر لینک‌های shadowsocks plaintext
  که رمزشان علائم نگارشی base64 (`=`، `%`) دارد اکنون ایمپورت می‌شوند. userinfo
  فقط زمانی به‌عنوان plaintext گرفته می‌شد که هیچ‌کدام را نداشت، بنابراین چنین لینک‌هایی
  به decoder base64 می‌رفتند و به‌عنوان خراب گزارش می‌شدند — اگرچه `:`
  خارج از هر الفبای base64 است و قبلاً شکل plaintext را اثبات می‌کند.

- `vmess://<base64>#Node 01` اکنون ایمپورت می‌شود: برچسب انتهایی باعث می‌شد
  payload به‌عنوان base64 نامعتبر خوانده شود، بنابراین گره کاملاً رد می‌شد. فیلد JSON `ps` همچنان غالب است،
  fragment قبل از پیش‌فرض `host:port` جایگزین است.

- یک payload `vmess` با nullهای صریح JSON (`"sni":null`، `"host":null`،
  `"ps":null`، همان‌طور که مبدل‌ها می‌نویسند) دیگر به متن literal `<nil>` در پروفایل تبدیل نمی‌شود.
  آن placeholder به SNI TLS و هدر Host می‌رسید و اتصالات را از یک لینک کاملاً خوانا
  خراب می‌کرد.

- `allowInsecure=true` رعایت می‌شود، نه فقط `allowInsecure=1` که این برنامه
  خودش می‌نویسد. حذف آن به معنای تأیید گواهی‌ای بود که لینک می‌گفت نه، که handshake را
  بدون هیچ سرنخی از منشأ آن شکست می‌داد.

- حذف کد مرده، شامل یک مجموع ترافیک Xray دوم که polling API loopback را
  به‌عنوان بایت‌های منتقل‌شده می‌شمرد.

- دانلودهای به‌روزرسان اکنون از یک لینک کند یا متناوباً مرده (داده‌ی موبایل، یک شبکه‌ی فیلترشده)
  جان سالم به در می‌برند. انتقالی که با صفر بایت برای ۳۰ ثانیه متوقف شود
  لغو می‌شود به‌جای مسدود کردن همیشگی — کلاینت باینری عمداً
  هیچ timeout کل-درخواست ندارد، بنابراین یک شبکه‌ی قطع‌شده قبلاً به‌روزرسانی را
  بدون راه خروج معلق می‌کرد. تلاش‌های ناموفق بایت‌هایشان را نگه می‌دارند و با یک درخواست HTTP `Range` ادامه می‌دهند،
  با backoff دوباره تلاش می‌شوند؛ منبعی که range را نادیده می‌گیرد،
  به یک `Content-Range` ناهم‌تراز پاسخ می‌دهد، یا دارایی را در میانه‌ی دانلود عوض می‌کند (که با `If-Range` گرفته می‌شود)
  به‌جای نصب بایت‌های splice‌شده یا ناقص، تمیز دوباره شروع می‌کند.
  پاسخ‌های دائمی (404) دوباره تلاش نمی‌شوند. پیشرفت و هر تلاش مجدد لاگ می‌شوند، بنابراین یک دانلود کند دیگر
  شبیه یک دانلود معلق به نظر نمی‌رسد.

- خطاهای دانلود و خطوط لاگ میزبان و مسیر را نام می‌برند، نه query را:
  لینک‌های دارایی GitHub به URLهای CDN امضاشده redirect می‌کنند که query string آن‌ها یک
  اعتبارنامه‌ی bearer است، و آن متن همان چیزی است که کاربران در گزارش باگ می‌چسبانند.

- نسخه‌ای که در کارت برنامه‌ی پایین-راست، تب About و متادیتای بسته‌بندی‌شده‌ی
  برنامه نشان داده می‌شود اکنون همه از یک جا می‌آیند. fallback هاردکدشده‌ی `1.0.0` فرانت‌اند
  و پسوند `-dev` پیش‌فرض Go نسخه‌هایی را ادعا می‌کردند که هیچ انتشاری هرگز نداشت؛ `wails.json` و manifest فرانت‌اند
  همچنان `5.11.28.3-fork.1` قبل-از-تغییر-نام را حمل می‌کردند. تست‌ها اکنون بیلد را شکست می‌دهند
  وقتی هر یک از این‌ها از `VERSION` منحرف شود.

- تب About یک کارت "Version stats" گرفت (برنامه، sing-box، Xray، mihomo،
  موتور فعال، OS/arch، Go runtime) با دکمه‌ی Copy diagnostics، بنابراین یک
  گزارش باگ کل تصویر را حمل می‌کند نه فقط نسخه‌ی برنامه.

- پروفایل‌های Aether با `tor="reverse"`، و `tor="chain"` همراه با
  `psiphon="chain"`، با یک `--tor-bind` یک پورت بالاتر از پورتی که برنامه dial می‌کند شروع می‌شدند:
  تخصیص‌دهنده‌ی پورت به‌جای یک مقدار، یک اشاره‌گر به cursor متحرکش تحویل می‌داد، بنابراین هر listener که یکی می‌گرفت
  *آخرین* شماره‌ی تخصیص‌یافته را می‌خواند نه شماره‌ی خودش. تونل روی
  پورتی پاسخ می‌داد که هیچ‌کس به آن متصل نمی‌شد و اتصال timeout می‌شد. تخصیص اکنون
  با رفتار post-increment کلاینت مرجع مطابقت دارد، و یک تست جدولی
  هر هشت ترکیب حالت tor/psiphon را تثبیت می‌کند.

- یک Disconnect که در حالی می‌رسد که یک connect هنوز موتورهایش را probe می‌کند دیگر
  CLI رسمی sing-box را در حال اجرا رها نمی‌کند. `CoreManager`
  پرچمی را که می‌گوید "ترانسپورت این گروه باینری بالادست است" فقط وقتی منتشر می‌کند که
  گروه را commit کند، بنابراین در کل پنجره‌ی probe، disconnect هسته‌ی سفارشی‌ای را که هرگز اجرا نشد متوقف می‌کرد و
  `sing-box.exe` را زنده پشت یک GUI "disconnected" رها می‌کرد — و چون آن manager
  همچنان خود را در حال اجرا گزارش می‌کرد، هر Connect بعدی با
  "upstream sing-box already running" شکست می‌خورد تا زمانی که برنامه دوباره راه‌اندازی می‌شد. هر دو
  باینری sing-box اکنون در آن مسیر بی‌قید‌و‌شرط پایین آورده می‌شوند، همان‌طور که پایه‌های Psiphon و Aether
  از قبل بودند (متوقف کردن یک manager بی‌کار یک no-op است). یک connect لغوشده‌ی Aether
  همچنین پورت تونلش را اکنون unpublish می‌کند: آن شاخه به‌جای خطای نام‌دار یک خطای تازه برمی‌گرداند،
  بنابراین rollback معوق هرگز اجرا نمی‌شد.

- پروفایل‌های VLESS با REALITY تیک‌خورده اما کادر TLS دست‌نخورده روی موتور sing-box
  به‌جای dial کردن plaintext به یک پورت REALITY متصل می‌شوند.
  sing-box `reality` را داخل `tls` تودرتو می‌کند، و گیتی که تصمیم می‌گیرد
  آیا `tls` اصلاً رندر شود `realityEnabled` را جا انداخته بود — مسیرهای Xray، mihomo و fingerprint
  همه آن را فهرست می‌کنند، بنابراین همان پروفایل روی آن موتورها کار می‌کرد و روی این یکی
  بی‌صدا شکست می‌خورد.

- رمزهای `vmess` به مقادیر موردقبول هسته‌ی sing-box تا می‌شوند.
  فیلد `security` آن یک enum حساس به حروف بزرگ و کوچک بدون fallback است، و
  `scy=` یک لینک عیناً ذخیره می‌شد، بنابراین املایی‌هایی که پنل‌های قدیمی همچنان منتشر می‌کنند
  (`chacha20-ietf-poly1305`، `AES-128-GCM`، `id-aes128-gcm`) کل کانفیگ را
  از بارگذاری شکست می‌دادند — پروفایل اصلاً نمی‌توانست متصل شود،
  در حالی که Xray همان فیلد را lowercase می‌کند و mihomo هشدار می‌دهد و پیش‌فرض می‌گذارد.

- تشخیص خودکار پروفایل loopback دیگر هسته‌ای را که کاربر انتخاب کرده بازنویسی نمی‌کند.
  ایمپورت‌های قدیمی dead-end (`trojan://…@127.0.0.1:40443` با
  هیچ چیزی که آنجا گوش نمی‌دهد) همچنان در پرواز به موتور SNI spoof تبدیل می‌شوند، اما
  روی پروفایل‌های Xray و mihomo هم فعال می‌شد: روی هر ماشینی که `sni-spoof.exe`
  نمی‌تواند راه‌اندازی شود (بدون باینری، بدون administrator برای
  درایور WinDivert) پروفایلی که قبلاً متصل می‌شد با
  "SNI spoofing requires administrator rights" شکست می‌خورد. یک ایمپورت کهنه فقط می‌تواند
  روی موتور پیش‌فرض برسد، بنابراین اکنون فقط آن یکی نجات داده می‌شود.

- پروکسی سیستم اکنون پذیرفته می‌شود، نه فقط ادعا. یک `ProxyEnable=1`
  که قبلاً `127.0.0.1:2080` خود NekoGo را می‌خواند — یک بازمانده‌ی NekoBox، یک
  نشست کرش‌شده که نشانگرش جان سالم به در نبرد، یا یک آدرس دست‌تایپ‌شده —
  بررسی "already ours, skip the churn" را بدون ثبت مالکیت برآورده می‌کرد،
  بنابراین `ClearSystemProxy` در Disconnect چیزی که مالکش باشد نمی‌دید، از عمل خودداری می‌کرد و موفقیت برمی‌گرداند:
  ماشین همچنان به پورتی اشاره می‌کرد که همین الان بسته شده بود، که از دست رفتن کامل اینترنت است
  نه یک تونل خراب. یک تطابق بدون مالک اکنون تصاحب می‌شود (وضعیت گرفته می‌شود،
  سپس در teardown پاک می‌شود)، و یک وضعیت قبلی گرفته‌شده که از قبل *همان*
  آدرس خود ماست دور انداخته می‌شود به‌جای برگردانده شدن.

- پروکسی قبلی OS در هر تصاحب دوباره خوانده می‌شود. قبلاً یک بار در هر فرآیند گرفته می‌شد و
  هرگز باطل نمی‌شد، بنابراین دومین چرخه‌ی connect/disconnect هر چیزی را که هنگام *اولین*
  connect آنجا بود بازمی‌گرداند — یا حذف می‌کرد، و بی‌صدا پروکسی‌ای را که کاربر
  هنگام خاموش بودن NekoGo پیکربندی کرده بود تخریب می‌کرد. snapshot اکنون دوباره توسط
  بازگردانی‌ای که آن را مصرف می‌کند پاک می‌شود.

- `GetSettings` sliceهای جدا‌شده تحویل می‌دهد. snapshot تنظیمات
  آرایه‌های subscription، Aether-scan، SNI و proxy-group خود را با
  مخزن به اشتراک می‌گذاشت، و نویسندگان قفل‌شده (`AddSubscription`، `TouchSubscription`،
  به‌روزرسان‌های scan-result و SNI) آن آرایه‌ها را درجا تغییر می‌دادند، بنابراین یک
  snapshot گرفته‌شده برای فرانت‌اند — یا تکرارشده در یک واکشی چندثانیه‌ای اشتراک — می‌توانست زیر خواننده تغییر کند و
  دوباره ذخیره شود مثل اینکه خودش نوشته شده باشد. فهرست‌ها اکنون در راه خروج کپی می‌شوند.

- گره‌های اشتراک توسط فید گروه‌بندی می‌شوند، نه توسط میزبان. یک فید تغییرنام‌یافته
  قبلاً بازخوانی‌اش را زیر نام قدیمی ثبت می‌کرد: گروه از میزبان URL مشتق می‌شد
  در حالی که نام نمایشی رکورد همان چیزی است که تب Proxies نشان می‌دهد، بنابراین یک اشتراک
  پس از تغییر نام به دو گروه تقسیم می‌شد.

- یک repoint به آدرسی که هیچ پروفایل قابل‌استفاده‌ای تولید نمی‌کند اکنون خودداری می‌کند
  به‌جای خوردن فید کارکننده. جریان قدیمی رکورد اشتراک را حذف می‌کرد و پروفایل‌های موجودش را
  روی URL مرده دوباره مهر می‌زد، بنابراین یک token چرخانده‌شده در کادر اشتباه به معنای از دست دادن هر گره از پنل بود.
  فید آدرس قدیمی خود را حفظ می‌کند و تعداد رد گزارش می‌شود.

- ایمپورت‌های لینک و اشتراک سریال‌سازی می‌شوند. ایمپورت‌های همپوشان مجموعه‌ی dedupe خود را
  *قبل از* واکشی می‌ساختند، `SaveProfile` فقط با ID تطبیق می‌دهد،
  و یک بازخوانی per-feed هرگز پرچم busy را که تایمر خودکار فرانت‌اند بررسی می‌کند تنظیم نمی‌کند،
  بنابراین یک دوبار-چسباندن یا یک بازخوانی که در میانه‌ی ایمپورت می‌رسد همان گره‌ها را دو بار الحاق می‌کرد — برای همیشه.
  یک ایمپورت دوم اکنون قبل از واکشی هر چیزی رد می‌شود.

- Plan A دیگر یک پاسخ DNS رهگیری‌شده را dial نمی‌کند. آدرس resolve‌شده‌ی decoy SNI
  همان endpoint اتصال است، و مسیر DoH هر IPv4 قابل‌تجزیه‌ای را می‌پذیرفت — بنابراین یک resolver مسموم
  یا یک captive portal که `127.0.0.1`، یک RFC1918 یا یک آدرس link-local پاسخ داده بود
  تونل را به interceptor (یا به یک پورت محلی بسته) تحویل می‌داد به‌جای شکست،
  و fallback آخرین-راه‌حل OS-resolver دقیقاً روی همان شبکه‌ای همین کار را می‌کرد که در آن تضمین‌شده دروغ می‌گوید.
  پاسخ‌ها اکنون با predicate‌ای که endpoint picker در Plan B همیشه استفاده می‌کرد گیت می‌شوند:
  رکوردهای غیرقابل‌استفاده رد می‌شوند، ارائه‌دهنده‌ی بعدی امتحان می‌شود، و یک
  مجموعه‌ی پاسخ که کاملاً غیرقابل‌استفاده است با آدرس‌هایی که داشت گزارش می‌شود.

- یک گزارش مرگ از یک موتور جایگزین‌شده دیگر اتصال زنده را تخریب نمی‌کند.
  کرش‌های موتور به‌صورت ناهمگام گزارش می‌شوند، بنابراین گزارش مربوط به فرآیندی که یک connect جدیدتر جایگزینش کرده
  می‌تواند بعد از commit آن connect برسد. `handleEngineExit` قبلاً
  پورت‌های dial loopback مشترک را به‌محض دیدن unpublish می‌کرد، قبل از بررسی generation که داخل teardown اجرا می‌شود:
  گروه جدید بدون front SNI و بدون listener Aether منتشرشده به کار ادامه می‌داد، بنابراین کانفیگ‌هایش
  direct رندر می‌شدند — "connected, no traffic"، یا یک پروفایل loopback که پورتی را dial می‌کرد که هیچ‌کس مالکش نبود.
  Un-publication اکنون فقط در دو جایی اتفاق می‌افتد که می‌دانند کدام فرآیند مالک پورت بود (reaper هر
  manager، value-scoped، و teardown گروهِ generation-checked).
  ناظر سمت App آن هم از سمت دیگر همین اشتباه را می‌کرد: یک گزارش مرگ که بعد از commit یک connect جدیدتر می‌رسد
  پروکسی سیستم ویندوز را برمی‌گرداند و بنر disconnect را به‌هرحال بالا می‌آورد،
  بنابراین ترافیک مرورگر بی‌صدا استفاده از تونل را متوقف می‌کرد در حالی که پنل همچنان
  آن را متصل نشان می‌داد و بایت‌ها را می‌شمرد. آن نصف اکنون فقط زمانی اجرا می‌شود که
  گزارش واقعاً چیزی در حال اجرا باقی نگذاشته باشد.

- همان ریس داخل یک probe زنده ماند. "Test" پروفایل spoof یک موتور یک‌بارمصرف می‌چرخاند
  وقتی هیچ‌چیز متصل نیست و پورت front کل-فرآیند را با یک موتور زنده به اشتراک می‌گذارد وقتی متصل است — اما teardown آن
  آن پورت را به‌محض دیدن پاک می‌کرد. یک connect که در حین probe commit شده بود پورت موتور خودش را منتشر کرد،
  و teardown probe پورت نشست زنده را با خودش پایین آورد،
  بنابراین گروه تازه‌متصل کانفیگ‌هایش را direct رندر می‌کرد. Teardown اکنون
  توسط value unpublish می‌کند: فقط پورتی که خودش نصب کرده بود.

- برگردان پروکسی سیستم اکنون قبل از نصبش ثبت می‌شود، و
  اتمیک نوشته می‌شود. رکورد کرش مقادیر پروکسی خود کاربر قبلاً
  *بعد از* commit شدن `ProxyServer`/`ProxyEnable` نوشته می‌شد، و خطای آن نادیده گرفته می‌شد —

  بومی `confirm`/`prompt` webview: دور انداختن یک پیش‌نویس کانفیگ
  (تعویض بخش، ترک Settings، ترک حالت)، بستن ویرایشگر پروفایل خام با JSON ذخیره‌نشده،
  اعمال یک کانفیگ ذخیره‌شده با یک reconnect، و نام‌گذاری یک گروه remark جدید در Profile tools.
  نام گروه به‌ویژه قبلاً از `prompt()` عبور می‌کرد، که WebView2 می‌تواند
  کاملاً رد کند — "New group…" سپس اصلاً هیچ کاری نمی‌کرد. Escape همه‌ی آن‌ها را لغو می‌کند،
  شامل آن ویرایشگر JSON، که قبلاً درخواست دور انداختن خودش را روی همان کلید دوباره باز می‌کرد.

- کارت "Active overrides" اندازه‌ی واقعی یک override ذخیره‌شده را گزارش می‌دهد.
  overrideها به‌صورت JSON تجزیه‌شده می‌رسند، بنابراین شمارش کاراکتر قدیمی
  طول `[object Object]` را چاپ می‌کرد — ۱۵ کاراکتر برای هر بخش، هر چه که داشت.
  هشدار کانفیگ خام از همان قاعده‌ی هسته پیروی می‌کند: یک override که `{}` یا `[]` دارد
  هیچ تنظیمی حمل نمی‌کند، بنابراین چیزی نیست که یک ذخیره‌ی خام آن را تخریب کند.

- ویرایشگرهای کانفیگ از پروفایلی پیروی می‌کنند که بک‌اند واقعاً رندر می‌کند —
  اتصال زنده اول، سپس انتخاب ذخیره‌شده، سپس اولین
  پروفایل — و آن را در سر کارت نام می‌برند. قبلاً انتخاب ذخیره‌شده را resolve می‌کردند در حالی که بک‌اند
  هسته‌ی در حال اجرا را resolve می‌کرد، بنابراین با یک پروفایل mihomo متصل و یک پروفایل sing-box انتخاب‌شده
  کارت ویرایشگرهایی را ارائه می‌داد که بک‌اند رد می‌کند، زیر نام پروفایل اشتباه.

- کلید حالت sidebar در هر دو حالت "Advanced Mode" نام دارد، با
  مقصد در tooltip آن. این یک کلید است که گزارش می‌دهد آیا Advanced روشن است، و
  قبلاً حالتی را که *به آن* سوئیچ می‌کرد اعلام می‌کرد:
  یک screen reader "Simple Mode, switch, on" می‌خواند در حالی که Advanced
  در حال اجرا بود، و متن قابل‌مشاهده با نام قابل‌دسترس موافق نبود.

- کارت‌های Backup & reset دیگر نوار اقدام چسبنده‌ی جدول Proxies را به ارث نمی‌برند.
  هر دو از `.nb-px-bar` استفاده می‌کنند، و قاعده‌ای که نوار اقدام انبوه را به پایین
  فهرست پروکسی پین می‌کرد unscoped بود، بنابراین هر نوار کارت Backup به viewport می‌چسبید و
  روی سر کارت خودش بالا می‌رفت — ۳۲ پیکسل از عنوان زیر دکمه‌هایی که به آن تعلق دارند پنهان می‌شد.
  چسبندگی اکنون `.nb-px-bar--sticky` است، که فقط توسط جدول Proxies پوشیده می‌شود.

- هر کارت Backup نتیجه‌ی خودش را گزارش می‌دهد. یک پیام واحد بعد از
  آخرین کارت می‌نشست، بنابراین Export "Exported to …" را ۵۱۰ پیکسل زیر دکمه‌ای که
  باعثش شده بود چاپ می‌کرد، بیرون از صفحه: کلیک شبیه این بود که هیچ کاری نکرد، و یک
  شکست طوری خوانده می‌شد که گویی Reset آن را تولید کرده. Export، Import، View raw
  config و Reset هر کدام خط خودشان را اکنون حمل می‌کنند.

- "View raw config" وقتی کانفیگی که نشان می‌دهد تغییر می‌کند دوباره می‌خواند. یک بار
  در هر کلیک واکشی می‌کرد و سپس منجمد می‌شد، بنابراین ذخیره یک override یا اتصال یک
  پروفایل متفاوت سند قدیمی را روی صفحه زیر عنوانی که وعده‌ی سند فعلی را می‌داد باقی می‌گذاشت.
  از همان قاعده‌ی هدف ویرایشگرها پیروی می‌کند و در تغییر هدف یا override
  تازه می‌شود — بی‌صدا، بدون غیرفعال کردن سه کارت دیگر در حین خواندن.

- ایمپورت یک backup اول می‌پرسد. تنظیمات و پروفایل‌ها را
  یکجا جایگزین می‌کند، به‌اندازه‌ی کارت Reset کنارش مخرب است — که یک `RESET-ALL` تایپ‌شده
  می‌طلبد — با این حال یک کلیک روی "Replace current data" آن را بدون تأیید انجام می‌داد.
  اکنون از دیالوگ خطر تم‌شده استفاده می‌کند؛ Cancel و ESC داده‌ها را دست‌نخورده و
  فایل انتخاب‌شده را همچنان بارگذاری‌شده رها می‌کنند. غیرمسلح کردن Reset هم توکن تایپ‌شده را پاک می‌کند، که قبلاً از
  غیرمسلح کردن جان سالم به در می‌برد: مسلح کردن مجدد یک جعبه‌ی پر و یک دکمه‌ی Confirm فعال ارائه می‌داد.

- حالت TUN متصل می‌شد اما چیزی بارگذاری نمی‌کرد. دو نقص در آنچه تونل
  از ماژول DNS می‌خواهد انجام دهد، هر دو با پورت کردن کانفیگ TUN پتن اصلاح شدند.
  اول، hijack فقط `protocol: dns` sniffed را تطبیق می‌داد، و inbound TUN
  آن پروتکل را برای یک مقصد تنظیم می‌کند — آدرس hijack که از آن مشتق می‌شود کنار آدرس رابط.
  یک query فرستاده‌شده به resolverی که OS از قبل داشت به‌عنوان DNS شناخته نمی‌شد و
  به پروکسی می‌افتاد. hijack اکنون پورت 53 را هم تطبیق می‌دهد، بنابراین یک query هر resolverی که
  به آن فرستاده شده باشد گرفته می‌شود.
  دوم، و دلیل اینکه هیچ چیزی بارگذاری نشد: بلوک DNS TUN یک سرور واحد بود، DNS-over-HTTPS با `detour: proxy`.
  وقتی آدرس پروفایل یک hostname است، sing-box باید آن را قبل از اینکه پروکسی بتواند dial شود resolve کند،
  و بدون `route.default_domain_resolver` از ترانسپورت پیش‌فرض بلوک DNS می‌پرسد — همان سرور DoH proxied.
  lookup روی اتصالی منتظر می‌ماند که برای برقراری‌اش وجود دارد، بنابراین هیچ نامی هرگز در حین بالا بودن
  آداپتور resolve نمی‌شود و هسته هیچ چیز اشتباهی لاگ نمی‌کند. TUN اکنون یک
  سرور bootstrap بدون detour کنار resolver proxied نگه می‌دارد و آن را در `default_domain_resolver` نام می‌برد،
  دقیقاً شکل `local-local` / `direct-dns-1` پتن، برای بلوک fallback و برای یک بلوک
  کاربر-پیکربندی‌شده که فقط یک سرور proxied دارد. queryهای hijack‌شده همچنان
  سوار پروکسی می‌شوند، بنابراین هیچ چیز درباره‌ی حفاظت از نشت تغییر نکرده، و حالت پروکسی
  بایت‌به‌بایت همان چیزی را رندر می‌کند که قبلاً رندر می‌کرد.

- حالت TUN همچنان متصل می‌شد و همچنان چیزی بارگذاری نمی‌کرد، و این بار
  stack دلیلش بود. NekoGo آن را به‌طور عمدی به `system` پیش‌فرض کرده بود تا
  CPU صرفه‌جویی کند؛ پتن به `gvisor` پیش‌فرض می‌کند. stack OS TCP را داخل ویندوز پایان می‌دهد:
  تونل SYN یک برنامه را به یک اتصال جدید خطاب به endpoint خود هسته روی آداپتور بازنویسی می‌کند،
  بنابراین handshake توسط OS تکمیل و بعداً بالا تحویل داده می‌شود — که آن را به یک اتصال inbound
  به باینری هسته تبدیل می‌کند، و ویندوز اتصالات inbound را فیلتر می‌کند.
  sing-tun تلاش می‌کند خودش آن را مجاز کند و خطا را دور می‌اندازد، بنابراین مجوز گمشده بی‌صدا است.
  یک connect با دسترسی بالا روی ماشین trace‌شده هیچ قاعده‌ی firewall `sing-tun` را قبل یا بعد از شروع نشان نداد، و
  همان اجرا به هر query DNS — UDP هرگز به listener OS نمی‌رسد —
  در حدود ۲۰۰ میلی‌ثانیه پاسخ داد در حالی که یک dial TCP به میزبانی که آن پاسخ‌ها نام می‌بردند پس از ۱۵ ثانیه
  timeout شد. این دقیقاً شکل "connected, nothing loads" است.
  اجراهای A/B روی هر دو stack و هر دو مقدار `strict_route` آن را حل می‌کند:
  `system` در probe TCP با strict routing روشن و خاموش شکست خورد، `gvisor`
  هر دو را پاس کرد، بنابراین strict routing هرگز مظنون نبود و `strict_route`
  بدون تغییر است. پیش‌فرض اکنون `gvisor` است، که TCP را داخل
  هسته پایان می‌دهد و هیچ چیزی از firewall لازم ندارد؛ `system` و `mixed` برای CPU و NAT خود قابل‌انتخاب می‌مانند،
  و ردیف Settings اکنون می‌گوید هزینه‌شان چیست — `mixed` همان listener OS را برای TCP embed می‌کند،
  بنابراین همان نیاز را به ارث می‌برد. تغییر پیش‌فرض، اما،
  نصبی را که روی آن trace شده بود اصلاح نکرد، و دلیلش ارزش ثبت دارد:
  NekoGo stack را قبل از وجود تنظیم هاردکد کرده بود، بنابراین اولین
  ذخیره‌اش `"tunStack": "system"` را در `config.json` نوشت مثل اینکه کاربر
  آن را انتخاب کرده باشد. یک مقدار ذخیره‌شده یک پیش‌فرض را می‌برد، و بررسی وجود یکی با الگویی که
  `"tunStack":"system"` را لازم داشت — بدون فاصله، در حالی که Go `"tunStack": "system"` می‌نویسد — کلید را
  به‌عنوان غایب گزارش کرد. بنابراین کانفیگ
  تمام مدت stack خراب را حمل می‌کرد و تغییر پیش‌فرض هرگز فرود نیامد.
  بارگذاری اکنون یک `system`/`mixed` ذخیره‌شده را یک بار به stack کارکننده migrate می‌کند،
  لاگ می‌کند چه کرد و چرا، و فایل را علامت می‌زند تا یک انتخاب عمدی بعدی System یا Mixed از آن پس
  رعایت شود به‌جای اینکه بی‌صدا در راه‌اندازی بعدی برگردانده شود. اینجا با راندن موتور واقعی تأیید شد:
  زیر `gvisor` probe TCP به peer می‌رسد (`read: EOF` — یک درخواست plaintext روی پورت 443 که Google بست، یعنی handshake
  تکمیل شد) جایی که زیر `system` timeout شده بود.
